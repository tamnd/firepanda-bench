The performance comparison for [firepanda](https://github.com/tamnd/firepanda), against pandas, Polars, DuckDB, cuDF and MojoFrame.

Two real public suites and one of our own run end to end today, on two machines. db-benchmark is the h2oai group-by and join suite as revived by DuckDB Labs. TPC-H is the specification's own query text, generated by DuckDB's `dbgen`, and every answer is checked against the validation output the TPC publishes with the specification. The third is ingestion, which is ours because no public suite measures CSV reading on its own, and it is the only one where firepanda is handed the same file as everybody else.

A full run is ten result files: db-benchmark and TPC-H in both io modes, ingestion in scan mode only because a memory mode for a suite that measures the reader would mean reading the file before timing the read, and all of it on two machines, an AMD EPYC VPS and an i9-13900K desktop. Nothing is averaged across a machine or across an io mode, because neither is comparable. The files are not committed to this repository. Each scheduled run uploads them as a workflow artifact and publishes the site from them, and [`results/README.md`](results/README.md) says what every file has to carry.

## The rule

**We publish the results we lose, and we publish what we could not run.**

A suite that only shows wins is not information, and anyone experienced reads it as an advertisement and discounts everything in it. Where pandas, Polars, DuckDB or cuDF is faster, the number goes in the table with a note about why, and if the reason is "not optimized yet" it says that rather than being omitted.

The same applies to coverage. firepanda cannot run TPC-H at all right now, so the TPC-H report has a firepanda column of twenty two explicit refusals rather than no firepanda column. An engine that is quietly absent from half a table looks like an engine that is fast on the other half.

## What we are measured against

| | Why it is in the table |
|---|---|
| **pandas 3.0.5** | The API being replaced and the audience being addressed. 3.0 is faster than the pandas people remember, so this is not a free win. |
| **Polars 1.44.1** | The performance bar, and the reference implementation of this design. |
| **DuckDB 1.5.5** | Correctness oracle as well as competitor, and the thing that wins TPC-H. |
| **MojoFrame** | The academic prior art in the same language. A production library that cannot beat a research prototype has not justified itself. |
| **cuDF** | The GPU comparison, from M9. Mature, and the honest baseline for any GPU claim. |

MojoFrame is in that table as a discipline rather than a courtesy. It supports all 22 TPC-H queries and its authors published where it falls behind, which is high-cardinality aggregation, and they diagnosed it as Mojo's dictionary. firepanda claims to have fixed that with its own hash table. The claim is only meaningful if we measure the query they lost on, which is TPC-H Q18.

Microbenchmarks are not here. They live in the main repository, because they run on every pull request and must not require Python or any competing engine.

## How a run is fair, and where it is not

**One process per engine and query.** Peak resident set is a high water mark on a process, so two engines sharing one interpreter cannot both be measured. The worker loads one engine, runs one query the requested number of times, and reports wall clock, resident set, peak resident set, user and system CPU, page faults and block IO per run.

**Every engine gets the same table.** In the default `memory` io mode the harness materializes each input to Arrow before the timer starts, so nobody is being timed on their Parquet reader. `--io scan` is the other mode, where Polars and DuckDB read Parquet themselves and push projections down, which is how they are used in practice. The mode is recorded in the result file, so a scan number and a memory number can never be mistaken for each other.

**Answers are fingerprinted across engines.** Each engine's answer is reduced to a row count, a sum of every numeric column and an order independent FNV-1a digest of every text column, all keyed by column name. Numbers are compared to a relative tolerance of a part in ten million, because engines add in different orders and pandas has to carry TPC-H money in float64; text digests are compared exactly. Engines that disagree are listed in the report by name, and the timings for that query are not treated as comparable. Sums and summed hashes rather than a hash of the sorted rows is deliberate, because it lets a Mojo engine compute the same value without reimplementing Arrow's sort.

**TPC-H answers are checked against the published validation output.** `pixi run validate-tpch` runs every query and compares it cell by cell to `tpch_answers()`, to a relative tolerance of a part in a million, including column names. All 66 implementations, which is three engines times twenty two queries, reproduce it at SF1.

Three places where the comparison is not perfectly even, stated here rather than buried:

**firepanda regenerates the db-benchmark data instead of reading it.** It has no Parquet decoder of its own. It has a Parquet reader, and that reader works by handing the file to DuckDB and taking the vectors back as Arrow, which is a reasonable thing for a dataframe library to do and not a thing we can put on a timer in a table where DuckDB is one of the four engines. So the driver reproduces the same rows from the same splitmix64 counter stream the generator used, before the timer starts, and the cross-engine fingerprint is what makes that claim checkable rather than asserted.

**pandas gets float64 money columns in TPC-H.** Arrow-backed pandas cannot do the decimal arithmetic that Q1 needs, because the intermediate wants precision 61 and Arrow's limit is 38, and there is no way to ask for a narrower one. So decimal columns are cast to double at load. That is faster than exact decimal arithmetic would be, so the bias runs in pandas' favour.

**firepanda runs 15 of 15 db-benchmark queries, 0 of 22 TPC-H queries and 5 of 5 ingestion queries.** q8 was the last db-benchmark gap and it closed when firepanda gained a per group top-n kernel. TPC-H needs the twenty two queries written in the driver and an ordering comparison on strings, and it needs a way to load the dbgen output that does not go through DuckDB. The report lists each one with the reason.

## Two methodology notes that decide whether the numbers mean anything

**Lazy engines must be forced to materialize.** ClickHouse and DuckDB use `CREATE TABLE ans AS SELECT` for this reason and our harness does the same. This is not theoretical for firepanda: after M4 the eager API is lazy underneath, so a benchmark that calls `df.groupby(...).sum()` and never looks at the answer measures plan construction and nothing else.

**The Mojo toolchain version is part of every result.** The Mojo ABI is not stable and the codegen changes release to release, so a result that does not say which compiler produced it is not reproducible. It is recorded in the results file alongside the engine versions, the CPU model, the core count, the governor, the transparent huge page setting and the turbo state.

Beyond that: fixed machines recorded in the results; the same machine for every engine in a given run, always; ten runs by default with the median reported and the full spread published, because a single number with no spread is not a measurement; Docker for the comparison engines.

## Running it

```sh
curl -fsSL https://pixi.sh/install.sh | bash
pixi install

pixi run env-report                                       # record the machine
pixi run data --suite tpch --size sf1                     # generate the dataset
pixi run validate-tpch --size sf1                         # check every answer first
pixi run bench --suite tpch --size sf1 --io memory --runs 5
pixi run report results/2026-08-28-*-tpch-sf1-memory.json
```

db-benchmark is the same shape:

```sh
pixi run data --suite db-benchmark --size 0.5GB
pixi run bench --suite db-benchmark --size 0.5GB --io memory --runs 5
```

`pixi run repro <results-file>` re-runs exactly the configuration that produced a given result file and reports any median that moved by more than a quarter. Anyone should be able to check any number we publish.

`pixi run check-sweep <results-file>` is the paranoia pass. It flags a speedup large enough to be a measurement error rather than a result, a run that covers too little of the suite to be quoted, a clean sweep, and any engine that raised. The first three go to a human, because each of them might be true. The last one fails CI as `check-sweep --crashes-only`, because an engine that raised is a hole in the table and in a report it reads exactly like a query the engine has not implemented.

## What not to do

**Do not benchmark against pandas 2.x.** It is what most people are running and it is not what we are competing with. Using it would inflate every number in a way that is indefensible the moment somebody notices.

**Do not benchmark the eager API without forcing materialization.** See above.

**Do not compare a `scan` number against a `memory` number.** They measure different work. The report refuses to put them in one table.

**Do not report a GPU number against a CPU baseline without also reporting cuDF.** The interesting comparison for a GPU dataframe is another GPU dataframe.

**Do not quote Mojo's marketing numbers.** Whatever the language's headline figures are, ours are the ones we measured on this library. Borrowing someone else's is how a project loses the benefit of the doubt on all of its own numbers.
